# Lessons

## Checking only the canonical config filename hides a non-standard one that IS loaded

- **Failure mode:** Auditing terminal-clear keybindings, I probed Ghostty for `~/.config/ghostty/config` (the documented auto-load path), found it absent, and concluded Ghostty was running pure defaults. The real, active config was `~/.config/ghostty/config.ghostty` — a non-standard name the user's setup still loads (confirmed because non-default keybinds/palette showed up in `ghostty +show-config --default=false`). I nearly wrote a redundant `config` file that would have diverged from the real one.
- **Detection signal:** `ghostty +list-keybinds | grep ctrl+shift+r` returned the user's CUSTOM macro (a non-default value), proving a config file WAS loaded despite the canonical path being absent. The decisive check is `+show-config --default=false` (what a file actually set) — not the presence/absence of the expected filename. Also: a bare `test -f <path>` and `test -e <path>` silently ran the project's `alias test="npm run test"` → jest, not the shell builtin.
- **Prevention rule:** To find which config a tool actually uses, ask the tool (`<tool> +show-config --default=false`, `--show-config`, `-vv`, etc.), don't infer from whether the documented filename exists — users alias, symlink, or point apps at non-standard paths. When a shell has `alias test=...`, invoke the builtin as `command test ...` or `[ -f ... ]` so config probes don't kick off a test run.

## "Keybinding doesn't work" can be a STALE shell, not a broken config — diagnose the byte first

- **Failure mode:** After editing `.zshrc` to bind `Ctrl+L` → `clear-screen`, the user reported it still failed inside tmux-in-cmux: Ctrl+L inserted a literal `^L` at the prompt. I started theorizing about tmux `extended-keys`/CSI-u re-encoding and nearly added speculative dual-bindings to the tmux layer. The real cause: the zsh sessions in those panes were started BEFORE the `.zshrc` edit (session created 08:17, edit later same day), so they never loaded the new bindkey. `Ctrl+L` self-inserting proves the byte arrived but no widget was bound in that shell.
- **Detection signal:** A `sed -n l` capture (press the key, read the literal bytes) showed `\f$` — i.e. Ctrl+L arrives as a clean `0x0c` form-feed through cmux→tmux→shell, NOT a CSI-u sequence. That single observation falsified the encoding theory and pointed at the shell binding. Always capture the actual bytes (`sed -n l`, `cat -v`, or `showkey -a`) BEFORE adding terminal-layer workarounds. A fresh `zsh -ic 'bindkey "^L"'` confirmed the config was correct, isolating the fault to the running session's age.
- **Prevention rule:** When a just-edited keybinding "doesn't work," first check whether the affected shell/multiplexer predates the edit — config changes don't retroactively apply to running interactive shells (`exec zsh` / re-source needed) or to a tmux server that hasn't `source-file`'d. Capture the real key bytes before assuming an encoding/re-mapping problem; don't stack CSI-u or user-key workarounds on a layer that's actually fine. Separately: a multiplexer-app key like Cmd+K (an app shortcut, not a terminal byte) cannot reach tmux as a keypress — to clear tmux's scrollback it must be routed as an escape sequence (Ghostty `super+k=text:\e[24;7~` → tmux `user-keys` + `bind -n UserN clear-history`), with a parallel zsh `bindkey` for the outside-tmux case.

## tmux full-clear: order matters — `clear-history` then `send-keys C-l` leaves the last screen

- **Failure mode:** A Cmd+K binding `bind -n User1 clear-history \; send-keys C-l` cleared the screen but left "some" scrollback. A tmux pane has two regions: the visible grid and the scrollback. `clear-history` empties only the scrollback; the subsequent `send-keys C-l` (shell clear-screen) pushes the still-visible grid UP into the now-empty scrollback — so the last screenful comes back. Empirically (200-line buffer, 120x30 pane): the buggy order left 28 lines; the correct idiom left 0.
- **Detection signal:** Reproduced by driving the running tmux server headless — `tmux new-session -d -s scratch`, fill with `seq 1 200 | echo line-$i`, run each candidate command, then `tmux capture-pane -p -S -1000 | grep -c line-` to count survivors. NOTE: `tmux send-keys -t s User1` does NOT fire a root-table _binding_ — it sends the key named "User1" as input to the pane's program. Root-table key bindings only trigger from a real attached client's keyboard, so verify the binding by running its _commands_ directly, not by send-keys-ing the key name.
- **Prevention rule:** For a complete tmux clear (visible + scrollback) use `send-keys -R \; clear-history` (the order the existing `prefix+L` already used): `-R` resets the visible grid WITHOUT pushing it to scrollback, THEN `clear-history` empties scrollback → 0 leftover. Do not use `clear-history \; send-keys C-l` — wrong order, and `C-l` re-pushes the visible screen into the buffer you just cleared.

## A "run it like last week's X km" pacing cue reads as a distance claim — name this week's distance, then the effort

- **Failure mode:** In a coach summary I wrote "Run Saturday like last week's 6 km" to convey *same easy effort*. The plan's Saturday was 7 km; the athlete read it as me calling this Saturday 6 km and corrected me. The week-4 coach block had the correct "Saturday's 7 km long run" one sentence earlier, but the trailing comparison silently overrode it in the reader's mind because the only number attached to the verb "Run Saturday" was last week's figure.
- **Detection signal:** Any phrase of the shape "[do this session] like last week's [N km/N m]" where N is the PRIOR week's volume, not the upcoming session's. The comparison number and the prescription number differ, and the comparison sits next to the action verb, so it gets mistaken for the prescription.
- **Prevention rule:** When referencing a past session for effort/feel, state the upcoming session's own number first and frame the past one explicitly as a contrast — e.g. "Saturday's 7 km — one km longer than last week's 6 km, same easy effort" — never "run Saturday like last week's 6 km." The only bare number next to the action verb should be the number the athlete is actually doing.

## A clean `refresh_errors: []` is not proof the data is fresh — a "successful" sync can silently skip the newest activities

- **Failure mode:** Running /coach, the engine reported `refresh_errors: []` and 20 activities, showing week 4 as 45% complete (Mon–Thu only). I took that as the truth and started a check-in built on "you missed Fri/Sat." The athlete had in fact run both — they just weren't downloaded. The Garmin OAuth token in `~/.garminconnect` had expired (last written 4 days earlier), and the coach engine calls the downloader with `--no-prompt`, which on a dead token raises `LoginUnavailable` and is caught as a *non-fatal skip* ("rebuild CSVs from .fit already on disk"). So the refresh "succeeded" by design while pulling nothing new, and `refresh_errors` stayed empty.
- **Detection signal:** The athlete contradicted the data ("Yes I did it. You didn't download the .fit files?"). Confirmable directly: the source `.fit` files in the log dir stopped at the same date as the CSV's last row, and `~/.garminconnect/garmin_tokens.json` mtime predated the missing activities. A direct token test (`Garmin().login(); get_activities_by_date(...)`) returned `GarminConnectAuthenticationError: Failed to retrieve social profile` — i.e. the cached token was dead, which the `--no-prompt` path swallows.
- **Prevention rule:** When an athlete reports a session the synced data doesn't show, trust the athlete and treat the sync as suspect *before* coaching on it — empty `refresh_errors` only means no *hard* failure, not that the latest activities arrived. Cross-check the newest `.fit`/log date against the athlete's claim and the token freshness. Auth fix: clear the stale `~/.garminconnect` token and re-auth (the expired token poisons even a fresh login attempt). And `.env.local`-style secrets MUST be single-quoted — an unquoted password containing `$`, `!`, or `^` gets mangled by the shell on `source` (here `$Q` expanded to empty → silent 401 "Invalid Username or Password"); single-quote, then verify the loaded length matches before trusting it. Never echo a secret to stdout for debugging — use `${VAR:+set}` / length checks instead (I leaked the password to the terminal via `${VAR:+yes}${VAR:-no}` concatenation).

## When an athlete retires a standing fact (injury/constraint), update the source profile and scrub the framing — don't just acknowledge it in chat

- **Failure mode:** The athlete's profile carried "lower back injury history — coach conservatively," so every session I planned around it and kept asking "how's the back?" When he said it was fully settled and to "plan as if I never had an injury," a chat-only "got it" would have left the constraint live: the profile still flagged it, the plan's "Listen to the body" box still read "at 57 with injury history," a fresh week-5 coach block still framed descents as "protecting your lower back," and the check-in thread "how did the descents feel (knees/back)" would have resurfaced next run. The skill reads injury history *from the profile* every run, so an un-updated profile silently re-injects the retired fact.
- **Detection signal:** The athlete declares a previously-tracked condition resolved and asks to stop factoring it — "consider X settled," "don't ask about it anymore," "plan as if it never happened." Any standing constraint in the profile, recurring check-in question, or coaching-prose motif tied to that condition is now stale.
- **Prevention rule:** Treat it as a durable update, not a one-turn acknowledgment. (1) Edit the source-of-truth profile to mark the fact resolved (dated) and instruct "do not treat as live / do not ask." (2) Scrub the framing from every generated artifact you control — coach blocks, principle boxes — and close the related open threads in the log. (3) Stop the check-in behavior going forward. (4) Distinguish constraint-driven caution from universal good practice: remove the former, but KEEP periodization (recovery weeks, gradual vert ramps) and universal form cues (ribs-down/flat-lumbar) — they're sound for any athlete. Do NOT silently make the plan harder just because a constraint lifted; if more load is wanted, offer it and let the athlete choose.

## The engine's per-activity zone label is an AVERAGE — it hides time-in-zone, so trail/vert runs read "easy" when they're actually Z3/Z4

- **Failure mode:** `parse-log.py` classifies each activity into a single HR zone from its *average* HR, and the weekly readout reports "% easy" / "polarized clean" off those labels. For steady flat runs the average ≈ the effort, so it's accurate. For variable climbing runs it is a fiction: Saturday's long run averaged 151 → labelled "Z2", and the week showed "100% Z2", but the athlete's actual time-in-zone was **23 min Z2 / 56 min Z3 / 15 min Z4** — a Z3 grind with a real threshold chunk. Coaching off the face-value label would have (a) hidden that the trail days carry the real intensity, (b) understated weekly hard-time that can blow past the 20% polarized budget, and (c) missed that the bit to manage is the sustained Z4 on the long day.
- **Detection signal:** The athlete volunteered it ("the Z2 you see is a session average; Sat was 23 Z2 / 56 Z3 / 15 Z4"). Confirmable from the data without asking: any activity whose **avg HR sits near a zone boundary while max HR is Z4/Z5** (Sat avg 151 / max 178), with **significant elevation** (508 m) and **slow or variable pace** (8:52/km with power-hike sections), is almost never a steady effort — the average is masking a wide spread. Flat runs with avg≈max and low elev are the only ones where the single-zone label can be trusted.
- **Prevention rule:** Do NOT treat the avg-HR zone label or the weekly "% easy" as true polarized compliance for trail/vert runs — it is an averaging artifact. For variable-terrain sessions read avg + max + elevation together and assume real Z3/Z4 time; reserve the "easy/Z2" reading for flat steady runs. The durable fix has now **landed in the engine**: the garmin builder writes an `hr_seconds` per-second-HR histogram per activity, and parse-log.py buckets it against the lab zones to produce per-run `time_in_zone` (the stacked zone bars in the logged table) and a week-level `polarized_time`. **Read `polarized_time` and the zone bars, not the avg-HR `polarized`/zone label.** Note the engine uses the *lab* zones from user.md, so the split differs slightly from Garmin Connect's configured zones — same shape, not identical numbers. On climbing terrain, accept some Z3 as race-specific (a vert race IS a Z3 effort) while still capping sustained Z4 on the long day and keeping the flat days genuinely easy.

## Never let a silent data gap reach the deliverable — if a source can't be read, fix it or make the hole visible, don't ask about it in the abstract

- **Failure mode:** Three of week 11's six vacation hikes were phone-recorded, so Garmin ships them as GPX only — no `.fit` — and the CSV builder reads `.fit` exclusively. I spotted the gap during the sync, asked the athlete whether to build a TCX fallback, and he reasonably declined ("just note it, vacation hikes are a one-off"). I then wrote the plan page showing 30.1 km / 1023 m. His next message: *"W11 doesn't show ALL the hikes, only Tue, Fri, Sat."* The real week was 42.1 km / 1854 m — a third of his volume and 45% of his vert simply absent from the log. The abstract question ("want me to fix the plumbing?") reads as optional engineering; the same question with the output in front of you ("your training log will show 30 km when you did 42") is obviously a yes. Worse, the same broken export was **aborting the entire download loop** — one activity whose zip held no `.fit` raised out of `download_all()`, so newer activities never downloaded and the CSV rebuild never ran.
- **Detection signal:** Any time a source file, row, or record is skipped, unreadable, or absent, and the artifact you're about to produce is a *summary or total* over those records. The tell is a per-item "skip"/"no data" log line that never surfaces in the rendered output. Also: a loop over externally-supplied items with an unguarded parse/extract step — one malformed item takes the whole run down and the failure looks like "nothing new to sync."
- **Prevention rule:** (1) When asking whether to fix a data gap, quote the *consequence in the deliverable's own units* ("the week will read 30 km instead of 42"), never just the mechanism ("no `.fit` for 3 activities"). Better still, if the fix is bounded, just do it and report it. (2) A per-item failure in a batch loop must be caught per item — skip, log, continue — never allowed to abort the batch or the downstream rebuild. (3) When a fallback source is less accurate than the primary (GPS-derived ascent vs. barometric), **calibrate it against records where both exist** and state the residual error in the artifact itself; here 3-point smoothing + 1.5 m hysteresis hit 1.7% mean error against three known-truth hikes, and that ±5% caveat went into the coach block so the athlete doesn't read a derived number as measured.

## Reporting a partial shortfall as a list of absent items reads as a data failure, not a training gap

- **Failure mode:** Week 15 had three planned gym slots and one logged session. I wrote "only Tuesday's makeup is in the log — Monday's Gym A and Thursday's Gym B are not." The athlete read that as *the Tuesday session failed to download* and replied "I did gym Aug 18, and it's on garmin connect, and you download it, something failed." He was defending a session that was present and correctly synced. The sentence put the one item that IS there in the same breath as two that are not, so the whole clause read as a sync complaint rather than a count.
- **Detection signal:** Any sentence of the shape "only X is in the log — Y and Z are not," where X is real data and Y/Z are things that never happened. The words "in the log" attach to the *logging*, not to the *doing*, so the reader hears a tooling problem. The tell in the reply is the athlete defending the data rather than the training.
- **Prevention rule:** Report a shortfall as a **count against the plan**, and confirm what IS present as a positive first: "one of the three gym sessions happened — Tuesday the 18th, logged and correct. Monday's and Thursday's did not." Never phrase the missing items as absent *from the log* when what you mean is absent *from the week*. And when the athlete does dispute the data, verify against the upstream source directly (`get_activities_by_date` on Garmin), not by re-reading the CSV the claim is already about — then say plainly that nothing failed.

## The coach decides; the athlete vetoes — polling the athlete with option menus abdicates the job

- **Failure mode:** Session after a hard week, I put four multiple-choice questions to the athlete in one screen — cap numbers, where to move vert, how to restructure a week — plus a second round for W18. He answered the first batch, then stopped the next one with "Why I have a coach if you ask me about what to do." The expertise he pays the coach role for was being handed back to him as homework.
- **Detection signal:** More than one AskUserQuestion round in a session, or any question whose options all sit inside the coach's own competence (structuring a week, where vert goes, which day rests). The athlete's answers arriving terse or annoyed is the late signal.
- **Prevention rule:** Reserve questions for facts only the athlete has (how it felt, schedule constraints, niggles) and for the rare decision that genuinely changes the plan's character. Everything else: decide, state what you changed and why, and let the athlete veto. One check-in round per session, max.

## On trail, planned distance is a target the terrain rounds — vert is the controlled variable

- **Failure mode:** Saturday came in at 28.6 km against a planned 25 and I framed it as running "3.6 km over plan." The athlete: routes are what they are — "3 +/- km is not a problem, +/- 1000 of elevation is." Treating the km delta as a compliance issue misread how trail days actually work.
- **Detection signal:** Any per-day comparison of actual vs planned km on a trail/mountain day being reported as over/under-delivery, especially within ~±3 km.
- **Prevention rule:** Judge trail days by vert and time on feet against the plan; treat distance within ±3 km as route noise (now codified as day caps in user.md). Reserve km-vs-plan language for flat, road-measurable sessions.

## When a derived artifact contradicts what the user just told you, fix the derivation — narrating the workaround is the smell

- **Failure mode:** The athlete opened with "week finished." I agreed, wrote "Week 17 closed" throughout the summary and the log — and then left the plan page showing week 17 with a **Current** badge, because `parse-log.py` still called it current. I even wrote the contradiction down as a feature: *"Pushed `week 18` to Garmin rather than week 17 — the engine still calls 17 current because Sunday is unlogged, but 17 is over."* He had already told me not to call current a week we agree is closed. Root cause: `week_complete_early()` advances the current week only when **every** planned non-rest day has a logged activity, so a week the athlete ends with a session deliberately dropped (heat, illness, travel) can never advance — and everything derived from `current_week` stays a week behind with it: `current_gym_file`, the editable window (`current+1..+3`), and which gym week gets pushed to the watch.
- **Detection signal:** **I wrote a sentence justifying why my output disagreed with the user's own statement of fact.** That narration is the tell — if the artifact needs a footnote explaining why it says something the user has contradicted, the tool is wrong, not the footnote. Confirmable without the user: `current_week == calendar_week` while the athlete reports the week is over, and the week's `logged_days` is a strict subset of its planned days that will never fill.
- **Prevention rule:** A user's declaration is **data** — record it at the source the engine reads (here `closed_through:` in `user.md`, honoured by `resolve_current_week`), never by hand-editing the rendered symptom, which the next sync silently reverts. When a derived value disagrees with the user, fix the derivation and let every dependent value follow; if you catch yourself explaining a deviation in a summary, stop and go fix the thing you are explaining. Corollary: a completion predicate built on "everything planned happened" needs a second, explicit way to be satisfied, because real weeks end with things deliberately not done.
